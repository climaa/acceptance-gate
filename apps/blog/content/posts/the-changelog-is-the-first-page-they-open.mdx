When someone opens the link to this repository, it is rarely to read code. It is a recruiter
checking whether a CV line is real, a tech lead deciding whether a call is worth thirty
minutes, or an engineer who followed a post here and wants to know what the thing actually
does. Three readers, three levels of patience, one URL.

For a while the honest answer to "where should that link point" was the README, which is
long, or the blog, which is opinion. Since the releases got a page of their own here last
week, the answer has been the [changelog](/changelog), and this post is about why a release
page — not a landing page, not a demo — turned out to be the one document that works for
all three.

## What v1.3.0 shipped

The headline of the latest release is short: **the visual-diff console has an end-user
manual, and it cannot drift from what it describes.**

The console is the tool this repo exists to run — it captures Storybook screenshot sets,
compares two of them, and renders the report a reviewer approves or rejects. Its behaviour
is specified in Gherkin feature files under `apps/e2e/features/acceptance/`, and those
files are executed by Playwright through `playwright-bdd` on every pull request. This is one
of the scenarios, verbatim:

```gherkin
Scenario: Deleting a held screenshot set is refused with the reason
  Given a screenshot set is held by a registered worktree
  When I delete the held set
  Then the deletion is refused naming what holds it
```

v1.3.0 adds `apps/manual`: three pages — console, report, sample mode — that are parsed at
build time from those same `.feature` files. The manual is not written; it is rendered.
Every step a reader sees on the manual is a step the acceptance suite ran against the
deployed console. If a scenario changes, the manual changes with the next build. If a
scenario is deleted, its page shrinks. There is no second copy of the requirements for
anyone to forget to update.

The mechanism is deliberately dull. An allowlist names which feature files are published
and how many scenarios each is expected to hold, so a scenario that silently disappears
fails the manual's own tests rather than quietly thinning the documentation. The step
renderer is a `packages/ui` molecule shared with the console itself, which is how the
console gained, in the same release, a plain explanation of what a run is, what A and B
mean, and what a verdict means — the same words, from the same component, on both
surfaces.

That is the feature. It is a good one, and it is not what this post is about.

## What the release page is for

Open [v1.3.0 on the changelog](/changelog#v1.3.0) and look at its shape rather than its
content. Every release since 1.0.0 has the same four parts, in the same order.

**A thesis line.** One sentence saying what the release is, before any version number or
PR list. For v1.3.0: _the console gets a manual, generated from what it already tests_. A
reader with fifteen seconds gets the story from this line alone, and a reader with fifteen
minutes gets the frame everything below hangs on.

**What earned the version.** A table of layers against pull requests: seventeen PRs
grouped into the eleven things they were actually for. This is the part that took me
longest to learn to write. A commit log is a record of what happened; this table is a
claim about why it mattered, and the version number is only justified if the claim holds.
"Minor" means the table has a row that adds behaviour. "Patch" means it does not.

**Index corrections.** The repository keeps a `PROJECT_INDEX.md` with file and test counts
per workspace. Every release lists which of those numbers were wrong at the previous
release and what they are now — `packages/ui` went from 492 to 512 tests, `apps/manual`
went from missing entirely to six files and sixty-nine tests. It is a small, boring table
and it is the most honest thing on the page: the documentation is treated as something
that can be wrong, and the release is where that gets audited.

**Known gaps.** What did not land. v1.3.0 says plainly that the design board for phase 5
was not updated before the console copy shipped, and why. A release that only lists wins
is marketing. A release that names the miss is a record.

None of this is novel. It is what a good release note looks like in any well-run open
source project. What was new to me was noticing which reader each part serves.

## Three readers, one page

**The recruiter** is checking one thing: is this person real, and do they ship. They cannot
evaluate `@gate/manual` and should not have to. What they can see is a date on every
release, a cadence between them — August 14, 27, 28, 31 — a thesis line they can read
without vocabulary, and a section that admits a miss. Those are the soft signals a CV
claims and cannot demonstrate: ships on a rhythm, writes clearly, does not hide things.
The changelog demonstrates them in under a minute, and does so without a single sentence
written for the recruiter's benefit. It is a side effect of writing the release for
myself.

**The tech lead** reads the table. They are asking whether I understand what a version is
for, whether I can group work into a narrative instead of a dump, and whether I separate
what changed from why. The index corrections answer a question they might not ask aloud:
does this person audit their own documentation, or only write it. The manifests note —
that every workspace is private, so the version is a coherence marker rather than a
distribution fact — tells them I know the difference between semver as a contract and
semver as a habit, and chose the habit on purpose.

**The engineer** uses the page as a map. PR numbers are cross-references, the compare link
at the bottom is the escape hatch to the real diff, and the known gaps are a lightweight
roadmap. The page tells them the repository is safe to explore because the description
matches the territory — which, as of v1.3.0, is now literally true of the manual as well.

There is a fourth reader, which is me in six months, wondering why `.fallow/churn.bin`
was untracked in v1.2.0. The release says. That is the reason to keep writing these even
in the months when nobody is hiring.

## The part I got wrong

Until this week the page opened with `v1.3.0`. A reader arriving cold — and the recruiter
always arrives cold — met a version number before they met the product, and had to infer
what acceptance-gate is from its release notes. That is backwards, and it took writing
this post to see it.

The fix is two sentences above the first release: what the repository is, and how to read
the entries below. Nothing in them is a version or a date, so they will not rot. It is the
smallest change in the repo this month and probably the one with the highest return per
line, which is a sentence I would not have believed before I started keeping a changelog
that people actually open.

If you keep a portfolio repository, write the release notes as if the release page is the
front door. On the evidence of this one, it already is.
