There is [a directory of agent skills for Next.js](https://www.ui-skills.com/skills/nextjs).
Three of them are published as the canonical set: `next-best-practices`,
`next-cache-components`, and `next-upgrade`. Two more sit downstream — an adoption skill and
an optimizer.

Only two of those five have anything to say about this blog. Deciding **which two, and saying
so out loud before running anything**, turned out to be the useful part of the exercise. A
skill you load without a reason produces advice you have no way to evaluate.

That paragraph is how this post started, and every sentence in it is out of date. I found that
out while installing the skills I had just written about, and it is a better finding than the
one I went looking for. The correction is in
[the last section](#the-directory-was-describing-a-past), left there rather than folded back
into the opening, because the order it happened in is the point.

What this post is, then: the two skills, the preconditions you need before pointing either of
them at an app, and the discovery that the directory advertising them was describing a past.
The Cache Components analysis itself — flipping the flag, what it broke, what the route table
looked like afterwards — is a separate piece of work and gets its own post.

## The two that apply

**[`next-best-practices`](https://www.ui-skills.com/skills/vercel-labs/next-best-practices)**
is a reviewer's checklist: file conventions, RSC boundaries, data patterns, the async request
APIs, metadata, route handlers, bundling. Twenty reference files. It carries
`user-invocable: false` in its frontmatter, which means you never type its name — it loads
itself when the work in front of the agent is Next.js code.

**[`next-cache-components`](https://www.ui-skills.com/skills/vercel-labs/next-cache-components)**
is the one with teeth. It covers the `cacheComponents` flag, partial prerendering, the
`use cache` directive, `cacheLife`, `cacheTag`, and the Next 16 deprecations around them:
`unstable_cache`, the singular `cacheHandler`, single-argument `revalidateTag`. Nothing in
that list is out of reach here: the
[root `package.json`](https://github.com/climaa/acceptance-gate/blob/main/package.json) already
wires `lint`, `typecheck`, `test`, `format:check`, `visual-diff` and `health:check` as separate
gates on a pinned Node and pnpm, and every one of them runs on every PR. The capability to adopt
all of this safely is in place and has been for a while. Worth stating up front, because it
means that whatever the analysis concludes, it will be a judgement about this app rather than an
excuse about its pipeline.

The other three do not apply, for boring reasons worth stating anyway. `next-upgrade` is
spent — this app is already on Next 16.3.0 and React 19.2.8, and
[that migration has its own scars](/blog/the-migration-that-passed-ci). The adoption skill
and the optimizer are both downstream of a decision I had not made yet: whether to enable
Cache Components at all. That is the decision this post is about.

## Before the analysis

Five things have to be true before the output of this analysis means anything. I learned
most of them by not having them.

**A build baseline you can diff against.** This is the one that matters. Without a route
table from *before* the flag, a green build afterwards reads as success, and it is not the
same claim. Mine:

```bash
✓ Generating static pages using 11 workers (18/18) in 733ms

Route (app)
┌ ○ /
├ ○ /about
├ ○ /blog
├   /blog/[slug]
│ ├ ● /blog/the-migration-that-passed-ci
│ └ ● /blog/visual-regression-with-agents
├   /blog/[slug]/opengraph-image
│ ├ ● /blog/the-migration-that-passed-ci/opengraph-image
│ └ ● /blog/visual-regression-with-agents/opengraph-image
├ ○ /rss.xml
└ ○ /sitemap.xml

○  (Static)  prerendered as static content
●  (SSG)     prerendered as static HTML (uses generateStaticParams)
```

Eighteen routes. Every one of them a file on disk at the end of the build. No `cookies()`,
no `headers()`, no `searchParams`, nothing read at request time anywhere in the app.

The `opengraph-image` rows are worth naming, because they are the ones that will matter later.
`opengraph-image.tsx` is a Next metadata file convention: it draws the social preview card for
a post — the image that appears when someone pastes the link into Slack or Mastodon — and Next
invokes it by convention, so nothing in the app imports it. It carries its own
`generateStaticParams`, and the comment above that function says why: the card should prerender
alongside the post it belongs to, "rather than on the first crawler request after a deploy".
That is a deliberate choice, written down, and it is the line item to watch.

**A version floor.** Cache Components wants 16.3 or later — that release is where the
top-level flag, `export const instant`, and the dev-overlay validation land.

**A grep for sync-IO, run first.** `Date.now()`, `new Date()`, `Math.random()`,
`crypto.randomUUID()`. These fail the build *even on routes you have opted out of
validation*, and no codemod fixes them. Finding them after you have started converting
routes means unwinding work.

**Translate, don't delete.** `cacheComponents: true` errors on any file still exporting
`dynamic`, `revalidate`, or `fetchCache`. The tempting fix is to delete the line that is
erroring. Each of those exports encodes behaviour the route is currently doing, and deleting
it silently stops the behaviour instead of moving it.

**The docs that shipped with your Next, not the ones in the model's memory.** Since 16.2 the
guides are bundled at `node_modules/next/dist/docs/`. This repo's `AGENTS.md` opens with a
blunt version of the same instruction, and it is right to: every claim in this post about
what the migration guide says was read out of that directory, at the version installed.

## The directory was describing a past

Everything above was written against the five skills named at the top. Then I went to install
them properly — committed into this repo rather than sitting in my own `~/.claude`, because
the sandbox that runs the autonomous agents here only ever sees committed git content. A skill
installed on my laptop does not exist inside it.

The install is where the premise fell over. `vercel-labs/next-skills`, the source the public
directories point at, is now three files and a redirect:

> # Next.js Agent Skills have moved
>
> The Next.js agent skills that used to live here now live in the Next.js repository, so they
> stay version-matched with the framework instead of drifting in a separate repo.

All three "canonical" skills are retired, and they were retired in two different ways:

- **`next-cache-components` was split**, into `next-cache-components-adoption` and
  `next-cache-components-optimizer`. Those are its successors. The two I filed above as
  "downstream of a decision I had not made" *are* the skill I had just spent two sections
  describing as the one with teeth.
- **`next-best-practices` and `next-upgrade` stopped being skills at all.** Their content now
  ships as the bundled docs under `next/dist/docs/` and the `AGENTS.md` / `CLAUDE.md` that
  `next dev` generates on 16.3+.

Read that second one against [what this post already told you to do](#before-the-analysis):
*read the docs that shipped with your Next, not the ones in the model's memory*. That
instruction was not an alternative to `next-best-practices`. **It is what `next-best-practices`
became.** This repo had already committed that replacement — `apps/blog/AGENTS.md`, landed
months earlier for the unrelated reason that leaving it untracked made every build dirty the
tree — which is why reading the shipped docs was available as a step at all.

So the honest version of the opening is: I set out to evaluate two skills, one of which no
longer exists and one of which had already become two. The analysis this was groundwork for is
unaffected — the flag, the blockers and the route table will not care what the advice was
called. But "which skills apply here" had a component I never thought to check, which is
whether the answer was still current. The directory was not wrong. It was describing a past, in
the present tense, with an install command that still worked.

What actually got installed, then — pinned, MIT, copied unmodified into `.claude/skills/`:

| Skill | Covers |
| --- | --- |
| `next-cache-components-adoption` | Enabling the flag and walking an app to a passing build |
| `next-cache-components-optimizer` | Tuning the static shell and navigation once it is on |
| `next-dev-loop` | Driving a dev-server iteration loop |
| `next-partial-prefetching-adoption` | Adopting partial prefetching |

That is the whole current set. None of the three retired skills came with it; vendoring one
would pin a superseded copy next to its own replacement. And the copies already on my laptop
turned out to be stale in a way I would not have noticed — at the pinned commit the optimizer
ships a `reference/` directory and two templates, where my installed copy still had the older
two-file layout. A `PROVENANCE.md` next to them records the commit and a checksum per file,
because the failure mode for vendored content is not "it breaks", it is "it quietly stops
matching upstream and nobody can tell when it stopped".
