An AI coding agent can load a 'skill,' which is a small bundle of expertise it pulls in when needed. Think of it as giving a contractor the current building code for their task, instead of relying on memory. Someone writes this guide once, publishes it, and all agents that install it follow the same instructions.

This project runs on [Next.js](https://nextjs.org/), and there is [a public directory of Next.js skills](https://www.ui-skills.com/skills/nextjs). Five of them. Three are presented as the canonical set; two sit downstream of those.

Only two had anything to say about this codebase. Deciding **which two, and writing down why before running anything**, is the part of this I would defend: a guide you load without a reason produces advice you have no way to evaluate. If you cannot say what you expected it to tell you, you cannot tell whether it was any good.

## The two I picked

[`next-best-practices`](https://www.ui-skills.com/skills/vercel-labs/next-best-practices) This document serves as a reviewer's checklist — the standards that a Next.js codebase is expected to adhere to, documented across twenty reference files. It is not explicitly invoked by name; rather, it automatically loads itself whenever the code being reviewed pertains to Next.js.

[`next-cache-components`](https://www.ui-skills.com/skills/vercel-labs/next-cache-components) It is the component associated with teeth. It encompasses a more contemporary framework feature pertaining to caching—the mechanism that determines which segments of a page are pre-rendered and which are assembled dynamically for each visitor. An incorrect configuration results in slow or outdated pages; accurately configuring this aspect constitutes a significant portion of what defines a "fast site."

Caching only sounds simple until you have to point at a specific piece of a page and say, with confidence, "this part never changes between visitors." That sentence is easy to say and hard to prove — unless the pieces were built to be pointed at. This is where a design system stops being a design exercise and starts paying rent. Every component in this project is catalogued and rendered in isolation, and each one is *presentational*: it receives everything it needs as inputs and fetches nothing on its own. A component like that produces the same output for the same inputs, every time, which is precisely the property that makes it safe to build once and reuse.

The [site header](https://acceptance-gate-storybook.vercel.app/index.html?path=/story/organisms-siteheader--default) and the [site footer](https://acceptance-gate-storybook.vercel.app/index.html?path=/story/organisms-sitefooter--default) are the obvious first candidates: they appear on every page and look identical for everyone who visits. The footer is the clearer case. It takes the year as an input rather than reading the clock itself — a deliberate choice, made years before caching was the question, so that its output would depend on nothing but what it was handed. That decision is the entire reason it can be cached now without anyone having to investigate whether it is safe. This is the argument for building [the design system](https://acceptance-gate-storybook.vercel.app/index.html?path=/docs/docs-system-design--docs) first rather than retrofitting one: when the catalogue already exists, identifying what to cache is reading, not archaeology — and performance work becomes a decision instead of an excavation.

Nothing in either guide was out of reach here. Every change in this repository already runs through the same automated gates on the way in — [the project's build configuration](https://github.com/climaa/acceptance-gate/blob/main/package.json) wires up type checking, linting, tests, formatting, a visual comparison against the previous build, and a code-health check, each as its own separate hurdle on every proposed change. That matters here for one reason: whatever the eventual answer about adopting the feature turned out to be, it would be a judgment about this application, not an excuse about its pipeline.

## Then I went to install them

I made two decisions at that point. First, where to store the files: either directly in the repository or just in my personal account on my laptop. Since this project runs autonomous agents in a sandbox, only what is committed is visible to them. Any guides or tools installed on my machine are invisible to the sandbox.

The second decision was made for me because the source indicated by the directory is no longer a skills library. Instead, it now consists of three files and a redirect.

> ## Next.js Agent Skills have moved
>
> The Next.js agent skills that used to live here now live in the Next.js repository, so they
> stay version-matched with the framework instead of drifting in a separate repo.

All three of the "canonical" skills had been retired, in two different ways. One was **split** into two successors with narrower scopes. The other two **stopped being skills altogether** — their content now ships inside the framework itself, which writes its own guidance file into every project it builds. We had already committed ours months earlier, for the entirely unrelated reason that leaving it untracked made every build appear to have uncommitted changes.

Here's the key insight: **nothing failed.** There are no broken links, errors, or warnings. The directory still shows all three items, and the install commands still function. When you run one, the files arrive intact and authoritative, but are no longer accurate. This type of failure is subtler than a 404 and more costly because the installed content appears current.

## What I installed instead

The four guides that currently exist are all identical copies, pinned to a single, specific published version.

| Guide | What it covers |
| --- | --- |
| `next-cache-components-adoption` | Turning the caching feature on, and getting to a working build |
| `next-cache-components-optimizer` | Tuning it once it is on |
| `next-dev-loop` | Verifying a change actually works in a running app |
| `next-partial-prefetching-adoption` | Loading the next page before the visitor asks for it |

None of the three retired ones came along; installing one would have placed an outdated copy next to its replacement. Nearby, there's a brief record of each file's origin, specific version, and a fingerprint — because the issue with copied content isn't failure, but that it gradually ceases to match the original without anyone noticing when this change occurred.

It's worth noting that the copies on my laptop were actually stale in a way I hadn't noticed before—same names, but different contents.

## The mistake I made

I considered "which guides apply here?" as a careful question, and indeed it was — I just answered it too superficially. There was a second part I never thought to ask: whether the answer remained current. The directory wasn't wrong exactly; it was describing a past situation in the present tense, with an install command that still worked. This reflects a common issue with AI tools: advice is easy to find, sounds convincing, but the effort to verify if it's still valid falls entirely on the user. That verification isn't optional; it's essential work.
