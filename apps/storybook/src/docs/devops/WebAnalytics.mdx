# Web analytics

All four published surfaces — the blog, the visual-diff console, the manual and this
Storybook — count page views with Vercel Web Analytics, and only on their production
deployment. Every preview is login-protected, so a view one could report is a reviewer or a
machine, and it would land in the same dataset as the live site where it reads as a reader.

That gate is the one thing all four share. Everything else on this page splits in two: the
three Next.js apps gate a React component at render time, and are what the measurements
below were taken from; Storybook has no React shell to put a component in and gates a
string at build time instead. The Next.js mechanism comes first; the section on the fourth
surface contradicts two of its conclusions, and says which two.

This is the only thing these sites do that phones home. It is cookieless and writes no
client-side storage, so it adds nothing to the one `localStorage` key each Next app's
`lib/theme.ts` already owns. There is no consent banner, and none is required.

## The gate, in the Next.js apps

`@vercel/analytics` decides development from production by reading `NODE_ENV` — which
every **preview** build also sets to `production`. Its own detection cannot draw the line
this needs, so `apps/blog/app/layout.tsx` draws it:

```tsx
<body>
  <SiteHeader brand={SITE_TITLE} nav={NAV} as={NextLink} />
  <main id="main">{children}</main>

  {process.env.VERCEL_ENV === 'production' && <Analytics />}
</body>
```

`VERCEL_ENV` is a Vercel [system environment
variable](https://vercel.com/docs/environment-variables/system-environment-variables).
Nobody declares it: it is injected into every deployment, and it is **absent** locally and
in CI — which is why the blog behaves identically on your machine before and after this
landed, and why the unit suite stubs it rather than reading one.

## What the gate does and does not buy

It withholds the **beacon**, not the **bytes**. Measured by building the blog with and
without the feature:

| Build                            | Scripts | Raw     | Gzip    |
| -------------------------------- | ------- | ------- | ------- |
| Without analytics                | 8       | 578,378 | 177,647 |
| With it, `VERCEL_ENV` unset      | 8       | 582,052 | 178,960 |
| With it, `VERCEL_ENV=production` | 8       | 582,052 | 178,960 |

The last two rows are identical. `process.env.VERCEL_ENV` is a runtime branch inside a
server component, so the client reference is registered at module level and the code is
emitted either way: **+1.3 KB gzip on every page load, in every environment**, including
previews that will never fire a beacon. Recovering it would mean a dynamic import, trading
1.3 KB for an extra request in production — not worth it at this size, but worth knowing
before someone reports it as a bug.

What the gate does buy on the transfer side is **no new request**: eight `<script>` tags
before and after. `@vercel/analytics` lands inside an already-required shared chunk rather
than one of its own.

## Two things that look wrong and are not

Both are properties of the component, so both are true of the three Next apps and neither
is true of Storybook — the first one is exactly inverted there.

**No `<script>` tag appears in any Next build's HTML.** Grepping a prerendered `index.html`
for `_vercel/insights` returns zero in production as well as preview. The component renders
`null` and builds the script element in an effect, appending it to `document.head` after
hydration. What the gate withholds is the component: production's RSC payload carries
`I[...,"Analytics"]` and names its chunk, a preview's does not. Do not read a missing
script tag as a broken gate — read the network log.

**Production ships a client-side bailout.** The component reads `useSearchParams`, which
under `cacheComponents` bails its own Suspense boundary out to client rendering. The
production `index.html` carries 491 bytes the preview one does not — a
`<template id="B:0">` placeholder and an `$RX(…, "BAILOUT_TO_CLIENT_SIDE_RENDERING")` call.
It is contained to that boundary, whose fallback is `null`; the route still prerenders
static. The package wrapping itself in `<Suspense>` is what keeps this from failing the
build, not what keeps it free.

## The fourth surface: Storybook

Storybook is not a Next.js app, so `@vercel/analytics/next` has nothing to attach to. It is
a static build with two halves: the **manager** (`index.html`), which owns the sidebar and
the URL, and the **preview** (`iframe.html`), which renders one story at a time. The beacon
goes in the manager, written there at build time by `managerHead` in `.storybook/main.ts`.

**The manager, never the preview, and this one is not a preference.** `previewHead` would
put the beacon in `iframe.html` — which is loaded once per story render, per docs page, per
theme, and once more for every shot the differ takes, because `capture.mjs` navigates it
directly rather than through the manager. One reader opening one docs page would report as
a dozen views, and a visual-diff run as a traffic spike. Injecting from the manager is also
what keeps the baselines clean: the manager is not in any capture's path at all.

**A plain HTML snippet, and no new dependency.** Vercel documents an HTML integration — a
queue stub plus a deferred `<script>` — and `.storybook/analytics-head.ts` emits exactly
that, modelled on the four functions in `@vercel/analytics` that decide the loader's URL.
Bump that package in the other three apps and those four functions are worth a diff against
this file.

**Here the gate withholds the bytes too**, which is the opposite of the measured result
above. There is no bundler that has already inlined the branch into a chunk: `main.ts` runs
in Node during `storybook build`, so a build without `VERCEL_ENV=production` emits the empty
string and the manager ships nothing at all. The 1.3 KB the Next apps pay in every
environment has no equivalent here.

**And the `<script>` tag _does_ appear in the production `index.html`** — the direct
inversion of the first caveat above. Grepping the built file is a real check here where it
proves nothing there:

```bash
VERCEL_ENV=production pnpm --filter @gate/storybook build
grep -c "vaq" apps/storybook/storybook-static/index.html   # 1
grep -c "vaq" apps/storybook/storybook-static/iframe.html  # 0, and this is the one to watch
```

The second line is the differ's guarantee, and it is worth running on both builds.

**Every URL here carries its page in a query parameter.** Storybook addresses pages as
`/index.html?path=/docs/...`, and `vercel.json` redirects `/` to exactly that — so reported
verbatim, the whole site collapses into one row in the Pages panel called `/index.html`.
The snippet registers a `beforeSend` that rewrites the reported URL to the origin plus the
`path` parameter, and drops the rest of the query, so
`/index.html?path=/docs/docs-devops-web-analytics--docs&globals=theme:dark` is reported as
`/docs/docs-devops-web-analytics--docs` — one row per page, not one per theme.

That function is inlined into the page through `.toString()`, which means the copy a reader
runs is re-parsed in an empty scope: it may close over nothing, and it must not throw,
because the loader calls it on every beacon. `analytics-head.test.ts` enforces both by
running the emitted script rather than the imported binding, and recovering the handler off
the queue it registers into — a closure that would work in the suite and fail in the
browser fails in the suite too.

## Why `turbo.json` names the variables

`build` declares `env: ["VERCEL_ENV"]`. Turborepo's builtin passthrough already forwards
`VERCEL_*`, so the gate reads correctly without it — but passthrough deliberately does not
**hash**. Without the declaration, all three environments produce one task hash, and a
shared remote cache is free to restore a preview-built artifact into production:

| `VERCEL_ENV` | Hash without `env` | With it            |
| ------------ | ------------------ | ------------------ |
| unset        | `45c84adffed7da93` | `307f0a1be1a7aa76` |
| `preview`    | `45c84adffed7da93` | `b43c776e6f983da3` |
| `production` | `45c84adffed7da93` | `3938daa03f6271c6` |

The cost is that a production deploy can no longer restore an artifact CI already built,
because their hashes now differ by design — roughly ten seconds of cold blog build per
production deploy. That is the trade: shipping a preview-built artifact to the live site is
the worse outcome.

`VERCEL_OBSERVABILITY_CLIENT_CONFIG` is named for the same reason and costs nothing extra.
It is the injected JSON that carries the obfuscated intake path, and only Storybook reads
it — the Next apps get the same value through the package, from a framework-prefixed copy.
Passthrough forwards it and, again, does not hash it: were Vercel to rotate that path, a
cache hit could restore an `index.html` carrying the old one, and the beacon would stop
arriving with nothing anywhere going red. Measured on `@gate/storybook#build`, with two
configs naming different script paths:

| Config | Hash without `env` | With it            |
| ------ | ------------------ | ------------------ |
| `/a`   | `46a7f388c5c54544` | `cce5bbfc371dccc3` |
| `/b`   | `46a7f388c5c54544` | `3999199efde3cd2b` |

Its cost is not zero, and the shape of it is worth writing down because it looks alarming
and is not. `build.env` is the **shared** task, so naming a variable there moves the build
hash of every workspace — the three Next apps and `@gate/ui` included, none of which read
this one. Two consequences follow, and only one is ongoing:

- Editing `turbo.json` at all marks every package affected, so all four Vercel projects
  redeploy once. That is the edit and not the variable: any change to this file does it.
- Were the intake path ever rotated, every workspace's next build would be a cache miss
  rather than only Storybook's. Affected-ness is computed from changed files and never from
  environment values, so nothing redeploys on that account — the cost lands on a build that
  was going to run regardless, and it is one cold build.

A `@gate/storybook#build` override would confine the second. It is deliberately not taken:
it would buy back a few cold builds of workspaces that were rebuilding anyway, at the price
of a second place where this task's configuration lives and can drift from the first.

Absent or unparseable, it falls back to `/_vercel/insights/script.js`, which Vercel's edge
still serves. That path is merely easier for a content blocker to recognise, so a fallback
is a quieter beacon and never a broken build.

## Verifying a change to any of this

No CI job sets `VERCEL_ENV`, so a green suite proves nothing about the production path.
Production is the one configuration nothing in the [gate](?path=/docs/docs-devops-the-gate--docs)
exercises. Run both sides by hand, filtering to whichever app you changed:

```bash
VERCEL_ENV=production pnpm --filter @gate/blog build
VERCEL_ENV=production pnpm --filter @gate/blog start
```

**The script path differs between local and production, and this is the trap.** Locally
the page requests `/_vercel/insights/script.js`, which **never resolves** — that endpoint
only exists on Vercel's edge, so what comes back is a 404 or a 503 rather than a script,
and the request being made at all is the proof. Do not read the failing status as a
failing gate. On the deployed
site there is no such request: Vercel rewrites the beacon to an obfuscated per-project
path, so you are looking for `/<hex>/script.js` and a `POST /<hex>/view` beside it.
Filtering a production network log for `_vercel` finds nothing and looks exactly like a
broken gate.

**On Storybook, the network log is only half the check.** Requests firing proves the
beacon; it says nothing about the `?path=` rewrite, which is the part that depends on
`beforeSend` being invoked for page views and not only for custom events. Those two fail
independently: if the rewrite is never applied, every request still arrives and the Pages
panel still collapses to a single `/index.html` row. Confirm the panel shows one row per
docs page once traffic has landed — that, and not the request count, is what says the
rewrite works.

Then repeat with `VERCEL_ENV` unset and confirm the request is absent. Without that second
half, the first proves only that something loaded.

**Check the served HTML, not the built file, on the console.** The blog's and the manual's
`/` are `○ Static`, so their prerendered `index.html` carries the payload line; the
console's `/` is `◐ Partial Prerender`, and the analytics boundary is a dynamic hole that
is simply not in the static shell. `grep`ping `.next/server/app/index.html` there returns
zero on a correct production build. Run the server and read what it serves.

Each Next app's `__tests__/analytics.test.ts` covers the same three branches at the unit
layer with the component stubbed, because the real one appends its `<script>` in an effect
no server render runs. They differ in renderer, and only one of them for a reason: the blog
and the manual use `renderToStaticMarkup`, the console `renderToReadableStream`, because
its sample-mode badge is an async component behind `<Suspense>` that the static renderer
cannot resolve.

Storybook's `__tests__/analytics-head.test.ts` covers the same three branches and rather
more, because here there is a real artifact to inspect rather than a stubbed component: it
parses the emitted head as HTML instead of grepping it, so a config value that escaped its
attribute reads as a new attribute and fails, where a substring match would pass.
