# Dependency bumps

Dependency maintenance runs through the same gate as feature work — a bump PR is not a
special case, it is the cheapest possible test of whether the gate means anything. A green
patch bump merges itself; anything that reds a check waits for a person.

The configuration is
[`.github/dependabot.yml`](https://github.com/climaa/acceptance-gate/blob/main/.github/dependabot.yml)
and
[`.github/workflows/dependabot-auto-merge.yml`](https://github.com/climaa/acceptance-gate/blob/main/.github/workflows/dependabot-auto-merge.yml),
both of which carry their reasoning in comments. This page does not restate what they say —
it covers the parts that are not visible in either file: why auto-merge needs a PAT, and
the failure mode that took this pipeline out silently for its entire life until it was
found. See also [The Gate](?path=/docs/docs-devops-the-gate--docs).

## Two kinds of ignore, and why the difference matters

`dependabot.yml` has two categories of ignore entry and the distinction is not cosmetic —
it decides what has to be true before an entry can come out.

**Blanket ignores** mean _a bump here is a hand-authored issue._ Landing one changes more
than a version number: a Playwright bump has to move the container image, the policy-sync
test and a mass rebaseline together, in one PR. There is no version of that which arrives
as a bot PR.

**Major-scoped ignores** — carrying `update-types: ["version-update:semver-major"]` — mean
something different: _the next major is blocked upstream, so there is no diff that makes it
work._ Minor and patch updates still flow. These exist because a blocked major otherwise
reopens every cycle, burning a full cold-cache run to rediscover a blocker that is already
written up in an issue, and leaving a permanently red PR on the board.

The removal criteria differ accordingly. A blanket entry comes out when someone decides to
do the work. A major-scoped entry comes out only when the checks written into its issue
start passing — and those issues carry the exact commands. Deleting one without running
them puts the red PR straight back.

## Why auto-merge runs on a PAT

Two non-obvious constraints, both of which have already been got wrong once.

**`GITHUB_TOKEN` does not trigger further workflows.** A merge performed with it is a
dead end: the push-to-`main` run that seeds the shared Turbo cache never fires, so every
bot merge would leave the cache cold for the next PR. A PAT-authored merge fires it.

**The PAT must live in the Dependabot secret store, not the Actions store.** Dependabot-
triggered runs read a different secret store. An Actions secret of the same name resolves
to an empty string — no error, no warning, the variable is simply blank. This is the same
mechanism that makes Dependabot runs build cold with no `TURBO_TOKEN`.

Because a blank credential produces a confusing `gh` auth error rather than a useful one,
the workflow has a guard step that fails with the fix instead. That guard is correct and it
worked. It still failed to tell anyone, for the reason below.

## The failure mode that used to hide itself

This was the part no file recorded, because it was an interaction between three mechanisms
that are individually fine — until a human does the one thing strict branch protection
makes reflexive.

Every step was working as designed. The guard failed loudly _while the actor was still the
bot_. Strict branch protection makes PRs go `BEHIND` on every merge to `main`, so
"Update branch" is the natural reflex. And the job's actor check is deliberate — a human
push to a bot branch **should** disable auto-merge, because the PR is no longer purely the
bot's work.

The result was that the one action a maintainer reaches for to unstick a bot PR was also
the action that hid why it was stuck. A misconfiguration that failed red on Monday was a
skipped check by Tuesday.

**Observed, not theorised.** Three runs on the same PR told the whole story:

| Run           | Actor             | Result      | What it means                                   |
| ------------- | ----------------- | ----------- | ----------------------------------------------- |
| `31681889445` | `dependabot[bot]` | **failure** | Guard fired: `GH_TOKEN` empty                   |
| `31686204691` | `climaa`          | **skipped** | Human updated the branch; failure now invisible |
| `31687240886` | `dependabot[bot]` | **success** | Secret fixed, branch recreated, `--auto` armed  |

The PR then merged itself. That was the first successful run of this workflow since it was
written — the secret had been in the wrong store from the beginning. It is also what
motivated the fix below: the guard should never have depended on who last pushed.

## Runbook: a bot PR that will not merge

Work down this list. The order matters, because the cheap options stop being available once
the expensive ones are needed.

**Is the auto-merge job skipping rather than failing?** Then a human has pushed to the
branch and the actor check is doing its job. Nothing is wrong with the workflow; the PR
needs a bot-authored update to recover. Check the `preflight` job's own checks — it stays
author-gated (not actor-gated), so it keeps running and, if a human push is why auto-merge
is off, its `::notice::` step names that explicitly rather than leaving you to infer it from
a skip.

**Never click "Update branch" on a Dependabot PR.** It permanently disables auto-merge for
that PR, hides any guard failure behind a skipped check, _and_ blocks the cheapest recovery
below. This is the single most useful thing on this page.

**`@dependabot rebase`** — the cheap fix, for a `BEHIND` PR whose branch carries only
`dependabot[bot]` commits. Updates against `main`, keeps the actor correct, preserves an
already-armed auto-merge. Dependabot refuses this outright on a branch a human has touched:
_"Looks like this PR has been edited by someone other than Dependabot."_

**`@dependabot recreate`** — the expensive fix, and the only one available once a human has
edited the branch. Discards the branch and rebuilds it from `main`, authored by the bot.
Everything on the old branch is thrown away, which is fine when the only human commit was
an "Update branch" click and is not fine otherwise.

**Closing and reopening the PR by hand does not work.** The workflow gates on
`github.actor`, and the actor of a manual reopen is _you_ — so the job skips again for
exactly the reason you were trying to fix. Only Dependabot acting restores the actor.

**Ordering, when merging something else at the same time.** Any merge to `main` flips an
open bot PR to `BEHIND`, and GitHub's auto-merge waits for checks but never updates a stale
branch. If a bot PR is armed and close to merging, let it land first — otherwise it sits
armed and stuck until someone issues a rebase.

## What closed the gap

The fix was not to change when auto-merge itself runs — a human push to a bot branch
**should** disable it, that part was always correct. It was to stop the credential guard
from sharing that same gate.

`dependabot-auto-merge.yml` now has two jobs instead of one:

- **`preflight`** is gated on the PR **author** only (`github.event.pull_request.user.login
== 'dependabot[bot]'`), which never changes no matter who pushed last. It asserts
  `GH_TOKEN` is present and, separately, emits an `::notice::` the moment the **actor**
  diverges from the author — the exact state that used to render as a silent skip. Both
  checks run independently, because a human push to a PR whose token is _also_ missing
  needs both diagnoses at once.
- **`auto-merge`** keeps the original, stricter gate — actor **and** author both
  `dependabot[bot]` — unchanged. It still disables itself the moment a human touches the
  branch, exactly as designed.

The guard can no longer go quiet just because someone clicked "Update branch": `preflight`
keeps failing (or noting) regardless, and its `::notice::` names the recovery path
(`@dependabot recreate`) instead of leaving a maintainer to reconstruct it from a skipped
check.
