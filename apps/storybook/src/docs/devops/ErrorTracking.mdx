# Error Tracking

Production errors from the blog land in **Bugsink**, a Sentry-compatible error tracker,
on its hosted free tier at `climaa.bugsink.com`. This page is the operational half of the
story: which tracker and why, how the instance is provisioned, how to verify the path
end to end, and the two caveats that verification actually surfaced. The code half — the
logger, the reporter seam, the adapter, and the bundle-size story — is
[Logging](?path=/docs/docs-devops-logging--docs), and nothing here changes any of it.

## The shape of the deployment

There is no server to run. The instance is Bugsink's hosted offering on its free
evaluation tier: 15K events a month, a single user, no credit card. One project exists,
`acceptance-gate-blog`, and its DSN is set in the Vercel project's environment variables
— `BUGSINK_DSN` (server) and `NEXT_PUBLIC_BUGSINK_DSN` (browser), production only, both
marked Sensitive.

That production-only scoping is the entire control surface. Local dev, CI, preview
deployments and sandbox agents have no DSN, so
[the adapter does nothing there](?path=/docs/docs-devops-logging--docs) — no SDK, no
reporter, no behaviour change. There is no second switch to keep in sync.

This blog's error budget is measured in events per month, not per minute; 15K is two
orders of magnitude above anything plausible. Be precise about what the per-project rate
limits (1,000 events per five minutes by default) do and do not protect: they cap
bursts, not the budget. A hostile client hammering the public, submit-only DSN could
exhaust the monthly quota in under two hours; the blast radius is that ingestion answers
`429` until the month rolls over and the tracker goes quiet — nothing is billed, since
no card is on file. At this repo's stakes that is an accepted failure mode, not a gap to
engineer against.

## Why Bugsink, and why hosted

The written research for this decision recommended GlitchTip, and the reversal is
documented rather than hidden — the comparison doc carries a supersession note, and the
[blog post about it](https://acceptance-gate-blog.vercel.app/blog/the-research-said-glitchtip)
walks through the whole arc. The short version, for the reader who just needs the
operational reasoning:

- **Scope.** This repo needs readable stack traces when a production error fires.
  Bugsink deliberately does errors and nothing else; GlitchTip's additional surface
  (uptime, performance transactions, OTLP logs) would be hosted, patched and backed up
  without being used.
- **The hosted free tier moved the maths.** Self-hosting either tracker means a VPS, TLS,
  backups, and — Bugsink's release train is notably security-fix-heavy — a patching
  obligation. The hosted tier makes all of that someone else's job at this volume. Terms as
  of 2026-08 — Bugsink names it an "evaluation" tier without publishing an expiry, so
  treat its durability as unproven; if the terms ever change, the reporter seam is the
  planned exit.
- **The known gap is priced in.** Bugsink cannot resolve Next.js production sourcemaps
  ([bugsink#133](https://github.com/bugsink/bugsink/issues/133),
  [bugsink#157](https://github.com/bugsink/bugsink/issues/157), both open and dormant).
  Browser frames arrive minified with no code context; server-side stacks are readable
  unminified, and those are the errors that matter most here — route handlers and Server
  Component renders fail server-side, while boundary-caught client errors serve as
  minified existence proofs. Do not invest in sourcemap upload while those issues stay
  open.
- **The exit stays cheap.** Every call site talks to `logger.error`; only the adapter
  knows Bugsink exists, and the adapter is Sentry-shaped. If the sourcemap gap starts to
  bite, the backend swaps without any app code noticing.

## Provisioning from scratch

The whole sequence, should the instance ever need recreating:

1. **Create the instance** at `bugsink.com/register/15K/` — subdomain, admin email, DPA
   checkbox. Access instructions arrive by email; there is no password at this step and
   no credit card at any step.
2. **Create the project** (`acceptance-gate-blog`). The defaults are right: team-members
   visibility, the latest (value-normalised) grouping mechanism, the stock rate limits.
   The SDK-setup page shows the DSN immediately.
3. **Set the DSN in Vercel** on the blog project, production environment only, as both
   `NEXT_PUBLIC_BUGSINK_DSN` and `BUGSINK_DSN`, marked Sensitive. The values are
   identical; the two names exist because the browser and server halves read different
   variables — see [Logging](?path=/docs/docs-devops-logging--docs) for why the public
   one must also be defined (possibly empty) in `next.config.mjs`. That define is
   already committed in both apps: re-provisioning changes no code, and the Vercel
   variables plus a redeploy are the whole procedure.
4. **Redeploy.** The browser half is a build-time constant, so the DSN takes effect on
   the next production build, not the next request. On the Hobby plan, confirm that
   deploy actually ran — a day that exhausts the deploy budget fails silently.

Deliberately **not** done: the DSN does not go into any `.env.local`. A local
`next build` + `next start` with a DSN would report development mishaps as production
errors; inert-by-default locally is the designed state, not an omission.

The visual-diff console ships the same instrumentation and is intentionally unwired — an
empty environment-variable list on its Vercel project is correct, not a gap. If it ever
needs reporting, create a **second Bugsink project** with its own DSN rather than
reusing the blog's: per-project attribution and rate limits are the point of projects.

## Verifying the path

Two probes in increasing order of realism, then the rule for reading a failure.

**1. Ingestion, without the app.** A minimal event posted straight to the DSN proves the
instance, project and key are alive:

```bash
curl -X POST "https://climaa.bugsink.com/api/<project-id-from-DSN>/store/" \
  -H "Content-Type: application/json" \
  -H "X-Sentry-Auth: Sentry sentry_version=7, sentry_client=manual-test/1.0, sentry_key=<key-from-DSN>" \
  -d '{"event_id":"<32-hex>","timestamp":"<iso8601>","platform":"javascript",
       "level":"error","exception":{"values":[{"type":"WiringTest","value":"safe to resolve"}]}}'
```

Both placeholders come from the DSN itself (`https://<key>@climaa.bugsink.com/<project-id>`):
the key is the segment before the `@`, the project id is the path segment after the
host. `event_id` is any 32 hex characters (`openssl rand -hex 16`), and the timestamp
must be roughly current (`date -u +%FT%TZ`). Expect a `200` with an event id, and the
issue in the dashboard seconds later. The SDKs use the newer `/api/<id>/envelope/`
endpoint rather than `/store/`; both accept events.

**2. The SDK, on the live page.** On the production blog, `window.__SENTRY__` existing
is already evidence — without a DSN the entire SDK is eliminated from the bundle, so its
presence proves the variable survived the build. An uncaught error thrown from the
console (`setTimeout(() => { throw new Error('test') })` — it must be uncaught, not
thrown inside the REPL's own try/catch) should produce a POST to `/api/1/envelope/` and
an issue tagged `environment: production`, `handled: false`.

**3. When step 2 fails, believe it selectively.** Check _which side_ refused
before blaming the wiring — which is the first caveat below.

## The two caveats verification taught

**Adblockers eat the telemetry, including yours.** The first live verification failed
five times from the maintainer's own browser while `curl` succeeded against the same
endpoint: privacy blocklists carry rules for Sentry's ingestion URL shape, and
`/api/1/envelope/?sentry_key=…` matches them. The instance root was reachable from the
page; the ingestion path specifically was not. A clean browser profile with no
extensions delivered the identical event immediately. Two consequences:

- When debugging "events not arriving", reproduce in a clean browser before touching
  the configuration — the failure may live in the observer.
- Client-side error counts **structurally undercount**. Some real fraction of visitors
  run the same blocklists. Treat the browser numbers as existence proofs, not rates;
  the server half has no such filter.

**The last-tick flush can lose an event.** The adapter starts a 2-second flush it
cannot await — both realms run the identical code, but the loss scenario is
server-specific: a Vercel function frozen immediately after responding can drop an event
captured on the request's final tick. This is the documented cost of using the slim SDK
pair instead of `@sentry/nextjs` — see
[Logging](?path=/docs/docs-devops-logging--docs) — and it is the first suspect if server
events ever go missing.

## Housekeeping

- **Quota:** 15K events/month on the free tier. The tracker going quiet mid-month with a
  `429` on ingestion is the symptom of hitting it — implausible at this volume, but that
  is where to look.
- **Users and access:** single admin (the maintainer's account — the tier allows exactly
  one user, which matches the repo). The login credential lives in the maintainer's
  password manager, never in the repo; the DSN itself is in Vercel's env settings and
  the repo-local root `.env`, which is gitignored.
- **Alerts:** Bugsink emails the admin on new issues by default — the project-membership
  setting "Send email alerts" ships as "Default (Yes)", verified on this instance. The
  dashboard is a second surface, not the only one.
- **Test issues:** resolve them after verification so the open list stays a signal. The
  first verification's issues are kept under the Resolved tab as a record.
- **Upgrades:** not this repo's job on the hosted tier — a feature of the tier rather
  than a footnote, given how much of Bugsink's release cadence is security fixes.
