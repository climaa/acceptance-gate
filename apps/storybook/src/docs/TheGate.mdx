# The gate

`.github/workflows/pr.yml` is the gate, and `gate` is the only **required** status check on
`main`. Everything else is arranged so that stays true: new checks join `gate`'s `needs:`
list rather than becoming required contexts of their own, which means tightening the merge
bar never requires a repository-settings change.

This page is the developer-facing half — what runs on your PR, what blocks a merge, and
the handful of invariants that look like style choices and are not. For the pixel side of
the pipeline see [Visual Diff Workflow](?path=/docs/docs-visual-diff-workflow--docs) and
[Diff Policy](?path=/docs/docs-diff-policy--docs).

## The jobs

Which jobs exist, and what each one runs, is
[`pr.yml`](https://github.com/climaa/acceptance-gate/blob/main/.github/workflows/pr.yml) —
read it there rather than here. Every job carries a comment explaining itself next to the
code it describes, which is where someone about to change one will actually see it. This
page would only be a second copy with a slower rot rate.

What matters for reading the graph above: `checks` is a **matrix** whose legs are the
per-command jobs; `sandcastle` and `e2e` are standalone because they need steps no matrix
leg wants; `visual-diff` runs alongside all of them and is deliberately outside
`gate.needs`; and `gate` is the aggregator, reporting even when a needed job fails —
`always()`, paired with the same draft guard every other job carries — and failing unless
every result is exactly `success`.

This page shows the mechanism, where the requirement that makes it binding is declared, and
what removing it costs. For the afternoon those conclusions came from — a supervised model
trying to skip the gate twice while the autonomous one never did, and what a branch
protection rule actually decides (nothing: no model evaluates the push) — see
[The guardrail you can switch off](https://acceptance-gate-blog.vercel.app/blog/the-guardrail-you-can-switch-off).

## Invariants that look cosmetic and are not

**`skipped` counts as failure.** `gate`'s guard treats `failure`, `cancelled` _and_
`skipped` as red. This is what makes the design safe, and it is also why no job in
`gate.needs` may carry an `if:` beyond the draft guard.

**Never put an `if:` on a matrix leg.** Matrix aggregation _ignores_ skipped legs:
`[success, skipped]` reduces to **`success`**. A future "skip `health` on docs-only PRs"
would produce a green `checks` containing a leg that never ran, and `gate` could not see
it. The job-level guard is the only guard, on purpose. Note the failure mode **inverts**
for a standalone job — a skipped job in `gate.needs` goes loudly red rather than quietly
green. Less dangerous, still unusable.

**`ready_for_review` and the draft guard are a matched pair.** Every job skips while the
PR is a draft, and GitHub counts a skipped required check as **passing**. Without the
`ready_for_review` event, a draft's skipped-therefore-green `gate` would still be standing
when the PR is marked ready — mergeable, having never run a check.

**`fail-fast: false` is load-bearing.** The default cancels the surviving legs on the
first failure. The run goes red either way, but losing the other five results defeats the
reason six checks exist.

**Never add a second required context.** A required context that never reports blocks
every PR forever, and it presents as a hung check rather than a misconfiguration. If a new
job should block merges, it goes in `gate.needs`.

## Where the requirement is declared

`pr.yml` decides what runs. It does not decide what _blocks_ — that is a repository rule,
and it lives outside the workflow entirely. The rule is committed as
[`.github/rulesets/main.json`](https://github.com/climaa/acceptance-gate/blob/main/.github/rulesets/main.json),
with the argument for each clause in
[its README](https://github.com/climaa/acceptance-gate/blob/main/.github/rulesets/README.md)
rather than restated here: one required context, no bypass actors, and no deletion or
force-push of `main`.

Two things about it belong on this page, because neither is visible from the file itself.

**Status: applied.** The ruleset is live — `main` runs on it, not on the classic branch
protection it replaced. Getting there was a six-step migration, executed and verified in
order: apply, confirm the drift check converges, verify on a throwaway PR that a red `gate`
is actually blocked, watch a real PR merge end to end, remove the classic rule, confirm it
is gone (`gh api .../branches/main/protection` 404s). Do not read the presence of the file
alone as proof of any of that — run the script, which prints the mismatches or says the
live rule satisfies everything the file declares.

**`bypass_actors: []` is a seatbelt, not a padlock.** Nobody bypasses the rule while the
rule exists, and whoever can delete the rule is exactly who it binds. That is not a flaw to
be engineered away. It is the ceiling on what any rule can do, and it makes the useful
question not _how strong is it_ but _what does it cost to take off_.

for.

## Removing the rule, and what could not be removed

The rule came off `main` for about two seconds one afternoon, deliberately, to purge a
string from the repository's history. Three calls: `gh api -X DELETE` on the protection,
`git push --force`, then `gh api -X PUT` to put it back. It was restored byte for byte
because the configuration had been written to a file first. That happened under the classic
branch protection this repo has since migrated off of — the mechanics below are the
ruleset's, but the shape of the argument is unchanged.

That is the disaster-recovery story, and it is also the measure of what a rule costs to
remove: one call, no confirmation, no second party, no audit entry anybody reads. The
ruleset's own version of that call is no smaller — `gh api -X DELETE
repos/{owner}/{repo}/rulesets/{id}` is exactly as fast, and `bypass_actors: []` has no
`enforce_admins`-style toggle to flip instead; the only lever is deleting or disabling the
rule itself. That is precisely why the ruleset README's break-glass path is a UI action
(Settings → Rules → the `main` ruleset → enforcement Disabled) rather than a script: turning
protection off is never something CI can do to itself. Set against it, the control that
actually holds.

**The agent's token carries four permissions.** Contents, issues, pull requests, metadata.
There is no `Administration` — the scope that edits branch protection or rulesets. The
distinction is not that the agent is instructed not to touch the rule. It is that it
cannot: the API returns 403, and no wording in any prompt changes that. It goes further
than that, in fact — confirmed while scoping the ruleset's own drift check:
`administration` is not a permission a workflow's `GITHUB_TOKEN` can be granted at all, at
any level. It parses only as a fine-grained-PAT or GitHub-App-installation scope, never a
workflow one.

**The asymmetry is the whole point.** Removing the rule is one API call from a session that
already holds the credential. Granting the permission that was never granted means going
back to GitHub, generating a new credential with a wider scope — a PAT, or an entirely
different credential type such as a GitHub App installation — and pasting it into the
secret store — several deliberate steps, each one an opportunity to notice what you are
doing.

**It got tested by accident.** A smoke-test issue asked for two things: a CI badge in the
README, and a repository description. The second half needs `Administration: write`. The fix
was not to widen the token — it was to cut the issue down to the half the agent was allowed
to do. A permission boundary is only real if you would sooner shrink the task than widen the
boundary. The same reasoning is why `--apply` is not wired into CI, and why the break-glass
path in the ruleset README is a UI action: anything that can turn the protection off from
inside the pipeline defeats it.

## Why `visual-diff` is exempt and `e2e` is not

Both drive Playwright. Only one blocks. The distinction is **baselines**.

A numeric pixel threshold stops being a safety net once change volume is high — an agent
refactoring thirty components in an afternoon — and approving a baseline has to cost the
same as reviewing a code diff: a person, in the PR, not a required check nobody reads
before merging. `visual-diff` still runs, still fails its own status loudly on a real
diff, and still posts its report as a sticky PR comment. It just never blocks on its own.

`e2e` has no baselines and nothing to approve. A failing scenario is a binary claim about
product behaviour — a heading is missing, a draft leaked onto the index, axe found a WCAG
violation — with a right answer that does not depend on taste. `visual-diff` exit 1 means
"a human must look"; an `e2e` failure means "the requirement is not met".

## The acceptance suite is guarded against itself

Because `e2e` blocks merges on a repo whose main traffic is agent-authored PRs, the
interesting question is not "does it pass" but "can it be made to pass without meeting the
requirement".
[`apps/e2e/scripts/suite-integrity.mjs`](https://github.com/climaa/acceptance-gate/blob/main/apps/e2e/scripts/suite-integrity.mjs)
runs before `playwright test` and closes the ways it can. Its header enumerates each
vector and the check that catches it; `apps/e2e/README.md` covers the same ground from the
suite's side. Both are one click away and neither can drift from the code, so they are not
reproduced here.

The design decisions behind it are the part worth arguing, and they survive any change to
the list:

**Exact equality on the scenario count, not a floor.** A floor decays — once ten more
scenarios exist, the original number permits deleting nine of them. Raising it alongside a
new scenario is a two-line diff; lowering it is a product decision and belongs in its own
hand-authored PR with the reason written down.

**Count scenarios, not Playwright tests.** Test count is a product of scenarios and
projects, so a legitimate `@desktop` tag changes it without any requirement changing —
which would train everyone to edit the number for non-events.

**Hermetic, about a second.** `playwright test --list` skips global setup, so nothing boots
a server or needs a browser binary. A guard that costs a real run is a guard someone
eventually removes.

Two Playwright settings carry the same intent. `forbidOnly` under CI closes `@only`, which
playwright-bdd translates straight into `test.only()`. And `failOnFlakyTests` with
`retries: 1` means a test that passed only on a retry **fails the run**. A retry cannot
tell infra flake from a genuine race in the product — it absorbs both, identically and
silently — so there is no way to swallow the first without also swallowing the second. On a
check that gates merges, and this repo auto-merges Dependabot PRs on `gate`, swallowing the
second is swallowing the finding.

**Several Playwright flags silently disable the empty-suite error** — the check that stops
a suite with no tests from exiting 0. The exact list is in `suite-integrity.mjs`'s
do-not-add note and in `apps/e2e/README.md`, next to the code that depends on it. The
general rule is the durable half: any flag that narrows or shards the run also removes
Playwright's own guarantee that it ran anything at all, so narrowing the acceptance suite
is never a performance decision.

## Dependency bumps run the same gate

A bump PR is not a special case — `--auto` still waits for `gate`, nobody bypasses branch
protection, and a red bump PR sits there like any other. Majors wait for a human
deliberately.

How auto-merge is wired, why it needs a PAT in a specific secret store, and the failure
mode where a correct guard goes silent are on their own page:
